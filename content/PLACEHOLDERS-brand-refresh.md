# Decisions — dash removal, brand colors, link audit

## What "remove all dashes" touched, and what it didn't

You confirmed this should cover both em dashes in prose and hyphenated compound words. Applied
across every page's visible text: headings, standfirst/body copy, button and link labels, status
pills, tier badges, table cells, meta descriptions and title tags, and every registry artifact's
title and description (including the six real AYENI deposits and the three demo entries, whose
`meta.yaml` files and `README.md`/`notes.md` content were edited). Em dashes became periods,
commas, or colons depending on what the sentence needed; hyphenated compounds became two words
("provider-level" to "provider level", "rule-based" to "rule based", and so on).

Deliberately **not** touched, because these are functional identifiers rather than prose:
- Registry identifiers (`AYENI-2026-0001`), matching the exact exemption you gave for that
  example.
- File and directory names and URL paths (`how-to-use/`, `module-01-account-takeover-and-
  synthetic-identity.pdf`). Renaming these would break every existing link and, for the six real
  registry deposits, would mean re-hashing and re-verifying already-published artifacts for a
  purely cosmetic reason. Hyphens in URLs and filenames are also standard web convention, not the
  typographic dash the instruction was about.
- CSS class names, HTML `id` attributes used as anchor fragments, and `aria-*` attribute values
  (implementation detail, never rendered as text).
- Code comments and `console.log` output in `build.js` (developer-facing only, never shipped to
  a browser).

The site's own name changed as part of this: "Open Fraud-Detection Methodology" is now "Open
Fraud Detection Methodology" everywhere it appears (browser tab titles, the header brand, the
home page hero and meta description).

## Two real registry files were edited, hashes regenerated

`REGISTRY-DEMO-0001/files/README.md`, `REGISTRY-DEMO-0001-v2/files/README.md`, and
`REGISTRY-DEMO-0002/files/notes.md` had dashes in their prose, so their content changed. Their
SHA-256 hashes were regenerated by `scripts/build-registry-metadata.js` (never hand-typed) and
independently cross-checked against `shasum -a 256`. The six real AYENI PDF files were never
touched; only their `meta.yaml` title/description text changed, which does not affect their hash.

## Print pages stay black and white on purpose

The purple/gold brand colors apply to every screen page. Print stylesheets
(`assets/print.css`, `assets/curricula-print.css`) still force pure black text on white, as they
did before this change: this was an explicit earlier decision for evidence-grade, printer-
economical output, not an oversight. Confirmed with axe and a computed-style check that this
still holds after the palette change.

## Color choices

Purple (`--accent`, `#5b2a86` light / `#c9a0f5` dark) carries every interactive element: links,
primary buttons, focus rings, section labels. Gold (`--accent-2`, `#d6a400` light / `#e8c34a`
dark) is used more sparingly, as a functional second color rather than decoration: it now
distinguishes Tier 2 (verified-institutions-only) registry badges from Tier 1 (public) ones,
which are purple, and it appears as a border accent on the brand mark and under section kickers.
A real bug surfaced and was fixed during this pass: `.btn-primary` and `.skip-link` hard-coded
white text against `var(--accent)`, which fails contrast in dark mode once `--accent` became a
light lavender rather than a dark teal. Fixed with a new `--on-accent` token (white in light
mode, dark purple in dark mode) and verified with axe in both color schemes, zero violations
either way. These exact hex values are easy to swap in `assets/styles.css` and
`assets/initiative.css` if you want a different shade.

## Full site link audit

Crawled 26 pages (every page type: home, about, curricula, how-to-use, all three initiative
pages plus the index, the registry index, every filter page, and every artifact page including
the six real AYENI entries) and resolved all 146 unique link targets found across them under
`file://` with no server. Every link resolves; the only `page.goto` "failures" were the `.zip`
download links correctly triggering a browser download instead of a page load, which is the
expected behavior for a download link, not a bug. Two previously dead anchors on the home page,
`#verify` and `#verification`, are fixed as part of this pass (see `PLACEHOLDERS-about.md`).
